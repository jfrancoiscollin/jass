# L3 — contextual replay + parent-anchor fit strategy

Date: 2026-08-20  
Status: implementation-ready, dormant until a new contextual corpus is certified  
Promotion: **not authorized by this document or PR**

## Question

When a new contextual corpus `D2` is available after a champion has already been fit on an older corpus `D1`, should Jass:

1. fit only `D2` while anchoring to the current champion (current continuation strategy), or
2. expose the optimiser to a small explicit replay memory from `D1` as well as the same parent anchor?

The primary hypothesis is that the champion is an incomplete compression of `D1`: a small explicit replay should reduce forgetting without drowning the new signal in a full-history refit.

## Primary causal contrast

Both arms use:

- the **same certified new corpus** `D2`;
- the **same target recipe**;
- the **same previous champion** as `--prior-mean`;
- the same architecture, exact fold, extras contract, phase model, L2, optimiser, convergence criteria and feature build;
- the same independent old/new holdouts for readout;
- no automatic promotion.

### A — CURRENT

Fit on every train row of `D2` only, using the current parent-anchor recipe.

Conceptually:

`L_A = L_D2 + anchor(theta, champion)`

This is the control and must reproduce the current continuation strategy.

### B — REPLAY25

Fit on:

- **100% of the `D2` train rows**;
- a deterministic, stratified replay subset `D1*` of the old train partition;
- sample weights that impose **75% effective loss mass on D2 and 25% on D1***;
- the **same parent anchor as A**.

Conceptually:

`L_B = 0.75 L_D2 + 0.25 L_D1* + anchor(theta, champion)`

The primary scientific contrast is `B - A`.  It isolates explicit data memory from the parent prior because the prior is identical in both arms.

## Why not concatenate D1 + D2 directly?

A raw union lets physical corpus size decide statistical influence.  If `D1` is much larger, new information is diluted even though much of `D1` is already represented by the current champion.  It also makes each L-BFGS pass increasingly expensive as history accumulates.

The replay design instead fixes the **effective loss mass**, not the row count.  The old replay row budget is chosen only for diversity/compute efficiency; sample weights guarantee the 25/75 objective even when whole-opening selection cannot hit the row budget exactly.

## Replay construction contract

Implemented by `tools/contextual_replay_mix.py`.

### No holdout leakage

The caller provides explicit `OLD` and `NEW` train-prefix counts from previously certified opening-level splits.  The mixer is forbidden to read rows beyond those prefixes into the output training dataset.

Old and new holdouts remain separate and immutable for evaluation.

### All new data retained

Every row in the `NEW` train prefix is copied.  The replay mechanism never down-samples the new corpus.

### Whole-opening replay

`OLD` is selected by `opening_id`, never by isolated records.  If an opening is selected, all of its rows in the old train prefix are retained.  This avoids pretending highly correlated positions are independent replay examples and prevents partial-opening leakage across selection boundaries.

### Target-independent stratification

Old opening groups are stratified using only board/provenance information available without labels:

- mean piece-count band: `opening_midgame`, `late_midgame`, `endgame`, `deep_endgame`;
- king exposure: `no_kings`, `mixed_kings`, `king_heavy`;
- provenance: `standard` vs `seeded`.

Stratum quotas track the old train corpus's record mass.  Within each stratum, openings are deterministically ordered by `blake2b(seed, stratum, opening_id)` and the nearest whole-opening prefix to the record quota is retained.

**WDL, score and contextual target values are not used for replay selection.**

### Effective mass

Default intended experiment:

- OLD effective mass = `0.25`;
- NEW effective mass = `0.75`.

For `n_old` selected rows and `n_new` new rows, the emitted float32 sample weights are proportional to:

- `w_old = 0.25 * (n_old+n_new) / n_old`;
- `w_new = 0.75 * (n_old+n_new) / n_new`.

`train_stream.py` already validates strictly-positive float32 sample weights, hashes them, normalises them to mean 1 on train rows only, reports row-level ESS and never applies them to the holdout.  No optimiser change is required.

### Target contract

If external contextual target sidecars are used, the mixer can copy OLD and NEW targets in exact record alignment.  This does **not** prove that the two target vectors were produced by the same scientific recipe.

The activation job must authenticate one of the following before fitting:

1. `D1` and `D2` targets were generated by the same target recipe/version; or
2. `D1*` was relabelled with the new recipe before mixing.

A mismatch in target semantics is a confound and must fail closed.

### Metadata

OLD and NEW game/opening identifiers are namespaced by source in the mixed sidecar so unrelated temporal corpora cannot collide accidentally.

If one source is JSM1 and the other JSM2, the tool refuses the mix unless `--downgrade-meta jsm1` is explicit.  Such a downgrade is allowed only after all JSM2-only contextual filtering/relabel work has already been completed.

## Activation command skeleton

The eventual certified job should construct B approximately as follows after authenticating and unpacking the two source corpora:

```bash
python3 tools/contextual_replay_mix.py \
  --old-data "$OLD_DATA" \
  --old-meta "$OLD_META" \
  --old-train-count "$OLD_TRAIN_COUNT" \
  --new-data "$NEW_DATA" \
  --new-meta "$NEW_META" \
  --new-train-count "$NEW_TRAIN_COUNT" \
  --old-share 0.25 \
  --new-share 0.75 \
  --seed "$LOCKED_REPLAY_SEED" \
  --old-targets "$OLD_TARGETS" \
  --new-targets "$NEW_TARGETS" \
  --out-targets "$WORK/replay-targets.npy" \
  --out-data "$WORK/replay.jnnw" \
  --out-meta "$WORK/replay.jsm" \
  --out-weights "$WORK/replay-weights.npy" \
  --manifest "$ARTEFACTS/replay-manifest.json"
```

The B fit then uses the existing trainer surface:

```bash
python3 pattern_jass/tools/train_stream_exact.py \
  --data "$WORK/replay.jnnw" \
  --feat "$WORK/replay.feat" \
  --target external \
  --target-values "$WORK/replay-targets.npy" \
  --targets-report "$ARTEFACTS/B-target-consumption.json" \
  --sample-weights "$WORK/replay-weights.npy" \
  --weight-min "$WEIGHT_MIN_FROM_MANIFEST" \
  --weight-max "$WEIGHT_MAX_FROM_MANIFEST" \
  --weights-report "$ARTEFACTS/B-weights.json" \
  --prior-mean "$PARENT_PJTW" \
  --prior-decay 0 \
  ...same fit recipe as A...
```

The control A uses the same new targets and same parent prior but no old replay and no non-uniform weights.

## Evaluation plan

### Static gates before strength games

Evaluate A and B separately on:

1. **OLD holdout** — forgetting/regression;
2. **NEW holdout** — adaptation to the new contextual corpus;
3. a declared balanced OLD/NEW diagnostic readout, if useful.

Use opening-cluster bootstrap where applicable.  Report both contextual-target log-loss and terminal-WDL diagnostics; neither replaces the strength gate.

### Primary strength gate

Only if the data/mixing/authentication contracts pass:

- A vs B on two fresh mutually disjoint opening pools;
- pools disjoint from fit/replay/holdout and prior force pools;
- paired colours;
- native budget primary, Q00 diagnostic if still part of the active project convention;
- no automatic promotion.

The primary question is simply whether explicit replay improves force over the current new-only + parent-prior continuation recipe.

## Optional diagnostic arms

These are **not required for the primary A/B** and should not delay it:

- `C — REPLAY25_NO_PRIOR`: same replay data/weights as B, no parent prior.  Separates explicit replay memory from parameter anchoring.
- `D — FULL_HISTORY`: full old+new union under an explicitly declared weighting rule.  Quantifies whether replay retains the useful part of a full-history refit at lower compute cost.

If run, these arms must be preregistered before seeing strength outcomes and receive the same fit/search budget convention as their intended contrast.

## Decision interpretation

- `B > A`, OLD stable, NEW stable/improved: explicit replay adds memory that the champion prior alone does not preserve.
- `B ~= A`: the champion prior is already a sufficient practical memory; keep the simpler CURRENT strategy.
- `B < A` with OLD better but NEW worse: replay is over-constraining adaptation; do not tune the 25% share on the same strength evidence.  A new independent dose experiment would be required.
- `B < A` everywhere: close replay for this corpus family.

The 25/75 ratio is the **first preregistered dose**, not a parameter to sweep post-hoc on the same pools.

## Scope of this implementation PR

This PR prepares the mechanism and tests only.  It does not:

- identify a future `D2` corpus;
- queue compute;
- refit a production model;
- read frozen cohorts;
- authorize promotion;
- alter the current CTX4 campaign.

Once a satisfactory new contextual corpus is certified, the activation PR should only need to pin immutable R2 identities/hashes, target-contract evidence, a replay seed and the existing fit/gate recipe.
